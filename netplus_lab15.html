Overview — what this lab is really teaching

This capstone pulls the toolkit together around a method. You'll use nslookup to verify and troubleshoot DNS, route print to read a host's own routing table, netstat to diagnose connections, and PowerShell to automate checks — then apply CompTIA's structured troubleshooting process on top.

The tools matter, but the method is what the exam rewards: identify the problem, theorize a cause, test the theory, plan and implement a fix, verify, and document.

CompTIA's 7-step troubleshooting methodology1) Identify the problem · 2) Establish a probable cause · 3) Test the theory · 4) Plan of action · 5) Implement the solution · 6) Verify full functionality · 7) Document findings. Know this order — it's directly testable.

Task 2.2 - Using route print to View Host Routing Tables

1 From the WinOS command prompt, type route print, and then press Enter. Notice that there are three sections of output. First, there is the Interface List (1), the IPv4 Route Table (2), and the IPv6 Route Table (3). We will explore each section in more detail.

2 The Interface List section displays all installed network adapters and MAC addresses of the host. Notice that there are three adapters: the vmxnet3 Ethernet Adapter (1), the TAP Windows Adapter V9 (2), and a Software Loopback Interface 1 (3). Please note that loopback addresses are created in software and have no physical MAC address.

3 Let's explore the IPv4 section. The IPv4 Route Table displays all active routes including the The 0.0.0.0 0.0.0.0 (quad zero) Network Destination represents the default route using the Gateway address of 192.168.1.254 (2). The Interface IP address (2) is the IP address of the local host (WinOS). The Metric (2) is a numeric value assigned to a route on an interface. In Windows, the metric value is based on link speed, and is also known as cost. It is automatically calculated. The lower the metric, the faster the link. The Network Destination of 127.0.0.1 (3) is the loopback interface and is used to test the NIC. The Network Destination of 192.168.1.0 (4) is the LAN network that this host Interface 192.168.1.20 (4) (WinOS) is connected to. The Network Destination of 192.168.1.255 (5) is the broadcast address used by WinOS to send packets to every device on the LAN. The Network Destination of 224.0.0.0 (6) are multicast addresses used to send packets to a specific group of hosts. The Persistent Routes section displays the default gateway address of 192.168.1.254 (7) used to get outside of the LAN to reach remote networks. This address is called persistent because it is explicitly configured in this host (WinOS). Remember the quad zero format of 0.0.0.0 0.0.0.0 as the Destination Network and Netmask combination represents the default route.

Note

Network Destination, Netmask (Subnet Mask), Default Gateway, Interface, and Metric (1).

📸 Screenshot for your report: route print showing the host routing table with the default route

4 The IPv6 Route Table section is displayed a bit differently than IPv4. The IPv6 Route Table displays all active routes including the If (Interface) number, Metric, Network Destination, and Gateway (1). The If number is the same as in the Interface List. The metric is computed the same as in IPv4. The ::/0 Network Destination represents the IPv6 default route using the Gateway address of 2000:9b32:c0e9:a::1 (2). Notice the Link-Local IPv6 address of FE80::250:56ff:fe99:40c1 (2) is also listed as a Gateway. The Network Destination of 2000:9b32:c0e9:a::/64 (3) is the Local LAN IPv6 network address. The Network Destination of Fe80::/64 (4) is the Link-Local LAN addrsess. The Network Destination of ff00::/8 (5) are IPv6 multicast addresses used to send packets to a specific group of hosts. The Persistent Routes section displays the Network Destination of ::/0 (6), the default route using the Gateway address of 2000:9b32:c0e9:a::1 (6) used to get outside of the LAN to reach remote networks. Remember the ::/0 represents an IPv6 default route.

5 To view the IPv4 routing table only, type route print -4, and then press Enter.

6 To view the IPv6 routing table only, type route print -6, and then press Enter.

7 Another way to view host routing tables is to use the netstat -r command. Notice that the output is exactly the same as route print.

Task 2.3 - Using netstat to Diagnose Connectivity

1 From the WinOS command prompt, type netstat ?, and then press Enter. All the options are listed and the purpose of each.

2 To display all connections and listening ports, type netstat -a, then press Enter. Four columns are displayed under Active Connections (1): the Proto (2) (Protocol) column displays both TCP and UDP connections, the Local Address (3) column displays the local addresses and port numbers for each connection, the Foreign Address (4) column displays other addresses in the local network or any other device this host communicates with as well as itself, and the State (5) column indicates the state of a TCP connection. Notice that the State is LISTENING for TCP connections. There are other states such as ESTABLISHED, CLOSED, AND

Note

MORE. UDP is stateless (connectionless), so it does not show anything under State.

3 Let's explore some more netstat options for TCP and UDP. Type netstat - a, and then press Enter. Look at the TCP connections. Look at the first LISTENING TCP connection (1). Notice the Local Address of 0.0.0.0:135. This represents a socket, which is a combination of an IP address and port number pair. The IP address of 0.0.0.0 is the default route and the 135 is the port number. A : (colon) is used to separate the IP address from the port number. The Foreign Address socket is WinOS:0 (self). The next LISTENING TCP connection (2) displays the Local Address socket of 192.168.1.20:139 (2), which is WinOS, and the Foreign Address is WinOS. The last LISTENING TCP connection (3) displays the Local Address socket of [::]:4966x (3), which is the WinOS IPv6 default route, and the Foreign Address is WinOS.

4 Look at the active UDP connections below. Similar to TCP, notice the Local Address default and :138 (2), and the Local Address sockets of [::]:500, 4500 and 5353 (3).

route sockets 0.0.0.0:500 and 4500 (1), the Local Address sockets of 192.168.1.20:137

5 To view interface statistics, type netstat -e, and then press Enter. The number of bytes, unicast packets, non-unicast packets, discards, errors, and unknown protocols received and sent are displayed.

6 The netstat -s command produces a lengthy output. To view more specific statistics, you can use more options. For example, if you want to view TCP statistics for IPv4, type netstat -s -p TCP, and then press Enter. Notice that important information is displayed, including active and passive ppen connections and failed xonnection Attempts (1). Also notice the number of reset and current connections (2). The number of segments received, sent, and retransmitted (3) are also displayed. One of the features of TCP is to retransmit dropped or missing segments.

7 To view TCP statistics for IPv6, type netstat -s -p TCPv6, and then press Enter. The same statistics are displayed for IPv6.

8 To view IPv4 statistics, type netstat -s -p IP, and then press Enter.

9 To view IPv6 statistics, type netstat -s -p IPv6, and then press Enter. In the next step, you will be using netstat in a practical way. You will establish a Secure Shell (SSH) connection from WinOS to pfSense, and view the connection statistics using the netstat command. SSH is an application that uses the TCP transport layer protocol for reliability.

Identify → theorize → test → plan → implement → verify → document.
Top-down vs bottom-up
Troubleshoot starting from the application layer down, or the physical layer up — pick based on symptoms.

Check yourself

1. List the CompTIA troubleshooting steps in order.

1) Identify the problem, 2) Establish a probable cause, 3) Test the theory, 4) Establish a plan of action, 5) Implement the solution, 6) Verify full functionality, 7) Document findings.

2. nslookup resolves a name correctly but the user still can't browse. Next check?

The client's own DNS cache/config — flush with ipconfig /flushdns and confirm the client is using the DNS server you just tested.

3. route print shows no 0.0.0.0 route. Consequence?

The host has no default gateway, so it can reach its own subnet but nothing beyond it.

4. Which PowerShell cmdlet combines a ping, a TCP port test, and route info?

Test-NetConnection — a one-cmdlet reachability-and-path check.

5. Why change only one thing at a time when testing a fix?

So you can attribute the result to a specific change — otherwise you won't know which action actually resolved the issue.
