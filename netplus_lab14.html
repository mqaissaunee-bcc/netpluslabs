Overview — what this lab is really teaching

Troubleshooting is mostly knowing which command answers which question. This lab drills the core toolkit on Windows (with Linux equivalents) so the right tool is reflex:

  • ipconfig / ifconfig / ip — what is my addressing?
  • ping — can I reach that host at all?
  • tracert / traceroute — where along the path does it break?
  • arp — what MAC maps to that IP on my local segment?
  • netstat — what connections and ports are open on this host?
Work the layers bottom-upCheck your own address (ipconfig), then the gateway (ping), then a remote host (ping), then the path (tracert), then name resolution. Isolating where it fails is half the battle.

Walkthrough

Adapter status & addressing

1Check adapter status and addressing

ipconfig
ipconfig /all

Linux equivalents: ip address show (or legacy ifconfig).

Reachability & path

1Ping a target

ping 192.168.1.254
ping 192.168.1.100

IPv6 works too: ping 2000:9b32:c0e9:a::1. 📷 screenshot for your report

2Trace the route

tracert 192.168.1.100

Linux uses traceroute. Each hop is a router decrementing TTL — the same mechanism you saw in Lab 1. 📷 screenshot for your report

ARP & connections

1Inspect the ARP cache

arp -a
arp -d

ARP maps Layer-3 IPs to Layer-2 MACs — essential for local delivery. Knowing it also explains ARP spoofing attacks (objective 4.2).

2List connections & ports

netstat -a
netstat -n

Combine as netstat -an to see every socket by number. 📷 screenshot for your report

Sends ICMP echo requests; replies prove Layer-3 reachability and show round-trip time.

Maps the hop-by-hop path using incrementing TTL; pinpoints where a path fails.
arp
Shows/edits the IP-to-MAC cache; the glue between Layer 3 and Layer 2 on a local segment.

Lists sockets, connections, and listening ports on the local host.

Where people get stuck

SymptomLikely causeFix
Ping to name fails but IP worksDNS problem, not connectivityResolution is broken — check DNS (nslookup), ipconfig /flushdns.
tracert hangs at a hopA router drops ICMP TTL-exceeded, or the path is down past that hopSome hops rate-limit/ignore ICMP; look at where it stops progressing, not a single *.
Ping blocked everywhereFirewall dropping ICMPA failed ping doesn't always mean 'down' — some hosts/firewalls block ICMP by policy.
Stale arp entryDevice moved / IP reassignedarp -d to clear the cache and force re-learning.

Exam relevance (N10-009)

  • Match the tool to the symptom — the heart of objective 5.5. Expect scenario questions.
  • Know Windows vs Linux equivalents (ipconfig↔ip, tracert↔traceroute).
  • Understand ARP's role and that arp -a reveals the IP↔MAC map (and underpins ARP spoofing).
  • Know netstat reveals open ports/connections, useful for both troubleshooting and security.

Check yourself

1. You can ping by IP but not by name. Which subsystem is broken?

DNS — connectivity is fine (IP works); name resolution is failing. Check DNS settings and flush the resolver cache.

2. Which command shows every hop between you and a destination?

tracert (Windows) / traceroute (Linux) — it reveals the path and where latency or failure occurs.

3. What does arp -a tell you, and why does it matter for security?

It shows the IP-to-MAC mappings your host has learned. Because ARP is unauthenticated, attackers can poison it (ARP spoofing) to intercept traffic.

4. Ping fails but the host is clearly up and serving web pages. Explain.

The host or a firewall is blocking ICMP. Ping isn't a definitive up/down test; try the actual service port.
